## Why

### The toolchain line

With Go 1.24.8, govulncheck v1.10.0 reports **84** reachable findings on
master: **43 in the standard library** (fixed in 1.26.9 or later) and 41 in
modules. With 1.27.4 the standard library has none; the 41 module
findings are step 2.3 (x/ family: note 06). Plan 04 said "~33" on
2026-11-19; more advisories have been published since.

Only the `toolchain` line moves; `go 1.24.0` stays. Nothing in this
change needs a newer language version.

### Go from go.mod in CI

The same arrangement as the console (#24, its note 14):

- **One place to change the version.** setup-go v6 reads `go.mod`,
  installs the **toolchain** line (1.27.4) from the runner's cache, and
  sets `GOTOOLCHAIN=local`. v5 installed the requested `1.24.x` (the latest
  patch, via `check-latest`), and the go command then switched to the
  toolchain line on its own.
- **A matrix of one Go version was only a label.** It is gone, and Go is no
  longer part of the job names. No branch protection refers to the names.
  `replication.yaml` had no other matrix, so its `strategy` block is gone.
- **A latent bug goes with it:** the two IAM import jobs
  (`iam-import-with-missing-entities`, `iam-import-with-openid`) have no
  matrix. `${{ matrix.go-version }}` was empty there, and they ran the
  runner image's preinstalled Go.
- `vulncheck.yml` said `cached: false`; setup-go's input is `cache`, so
  caching was on. Fixed. govulncheck is pinned to v1.10.0 instead of
  `@latest`, as in the console.
- `mint.yml` is disabled in the fork (no `mint` runner); changed the same
  way so that no 1.24 is left behind.

Every Go-running job has setup-go. The workflows without it
(depsreview, helm-lint, issues, lock, shfmt, typos) run no Go.

### Test harness image

The `golang:*` images set `GOTOOLCHAIN=local`. With `golang:1.24`, the
harness would ignore the toolchain line and keep testing with 1.24. The
image is now the exact `golang:1.27.4`.

An existing local `fork/test/.env` is an untracked copy of the example and
keeps `golang:1.24` until it is changed the same way.

### golangci-lint v2.15.0

v2.11.4 is built with Go 1.26 and refuses to start:

```
can't load config: the Go language version (go1.26) used to build
golangci-lint is lower than the targeted Go version (1.27.4)
```

The toolchain line alone triggers this; the `go` line is still 1.24.0.
v2.15.0 is built with Go 1.27.0.

The pin had been held at v2.11.4 because `install.sh` from v2.12.0 on
failed its checksum step (note 02). v2.15.0's `install.sh` matches the
checksum line to the end (`grep "${BASENAME}$"`), so the `.sbom.json` line
no longer matches too, and the install works. The Makefile comment says
so.

`gomodguard` is deprecated since v2.12.0 in favour of `gomodguard_v2`. It
has no settings in `.golangci.yml`, so both are no-ops; the switch clears
the warning. Unlike the console, this config already ran staticcheck with
`all` minus a list, so no scope pin was needed.

### What the new linters found

The new linter versions report findings in unchanged code:

- **gofumpt**, 12 files: parentheses around a single operand are now
  removed, e.g. `(xnet.Port(opts.Port))`, `(z.VersionID)[:]`,
  `^(syscall.O_DIRECT)`. Applied with `golangci-lint fmt`; the syntax tree
  is the same. `docs/debugging/inspect/export.go` has the same pattern, but
  it is a separate module that `make lint` does not cover, so it is left
  alone.
- **SA4006**, `cmd/os-readdir_test.go`, 3 sites:
  `testResults = append(testResults, …)` right before `t.Fatalf`. The new
  staticcheck knows that `t.Fatalf` does not return, so the value is never
  used. The comment said it was needed "for cleanup", but the directories
  come from `t.TempDir()`, which the testing package removes. Both lines
  go.

### TestTrackingResponseWriter

The full unit suite on Go 1.27.4 failed exactly once:

```
--- FAIL: TestTrackingResponseWriter
    api-response_test.go:140: Write unexpectedly failed: http: request method
    or response status code does not allow body
```

Since **Go 1.26**, `httptest.ResponseRecorder.Write` returns
`http.ErrBodyNotAllowed` after `WriteHeader` with 1xx, 204 or 304, as a
real server does. Checked in the images: absent in `golang:1.25.0`,
present in `golang:1.26.0`. The test used 123, an arbitrary 1xx, and then
wrote a body. `trackingResponseWriter` only forwards both calls, and the
test checks that it does. Status 299 keeps the "unusual status" intent and
allows a body.

The gofumpt, SA4006 and TestTrackingResponseWriter changes are our own;
upstream minio/minio has no newer commit (its master is contained in
ours).

### stringer, outside the dependency graph

With the toolchain and lint fixed, `make verifiers` still failed, in
`check-gen` (`go generate ./...`):

```
stringer: internal error: package "context" without types was imported from "command-line-arguments"
cmd/api-errors.go:81: running "stringer": exit status 1
```

Upstream (`f01374950`, 2025-04-25) lists stringer and msgp in go.mod's
`tool` block, and `main.go` runs `//go:generate go install tool` first,
which installs both for the bare `stringer`/`msgp` directives. stringer is
then built from the module's own golang.org/x/tools, **v0.32.0**, which
cannot load Go 1.27's standard library. The 19 stringer directives failed;
the 36 msgp directives did not. On master with Go 1.24.8, `go generate
./...` passes.

Measured with stringer on the `internal/grid` directive under Go 1.27.4:
x/tools v0.32–v0.44 fail; **v0.45.0** and later work.

Raising x/tools in go.mod would put a newer x/tools in the server's
dependency graph. Every working version requires `go >= 1.25` and newer
x/mod, x/net, x/sync and x/sys, so the x/ family the server links would
move with it:

- v0.45.0, the minimum, moves x/net to 0.54, which **does not build** here:
  under Go 1.27, x/net 0.54 compiles its own HTTP/2 server only with the
  `http2legacy` tag, and grpc 1.72 uses `http2.TrailerPrefix` from that
  file;
- v0.53.0 builds, but moves x/crypto 0.37 → 0.59, x/net 0.39 → 0.63,
  x/text 0.24 → 0.44, x/sys, x/sync, x/term, x/mod, and the `go` line to
  1.26.0.

Either way it is a runtime change, for a build tool. Instead, stringer
leaves the `tool` block and `main.go` installs it right after upstream's
line:

```go
//go:generate go install tool
//go:generate go install golang.org/x/tools/cmd/stringer@v0.53.0
```

`go install pkg@version` builds outside the current module, so x/tools
v0.53.0 and its dependencies never enter the server's graph. go.mod loses
one `tool` line; x/tools stays at v0.32.0 (msgp requires it); go.sum is
unchanged. The 19 directives are unchanged. The installed binary was
checked: `go version -m` shows `golang.org/x/tools v0.53.0`.

This also keeps the next Go release from forcing a runtime dependency
change through a generator: the generator's version now moves on its own.

### Regenerated stringer output

The stringer from x/tools v0.53.0 writes the 19 `*_string.go` files
differently. `String()` now computes a local `idx := int(i) - <offset>`
instead of indexing with the receiver, or decrementing it, as in
`internal/grid/msg_string.go`, whose `Op` starts at 1. The names, the
index tables and the result for every value are unchanged. The output is
committed as generated.

`make check-gen` compares only `*_gen.go` (msgp output, unchanged) and
`go.sum`, so it would not have caught these files. They are committed so
that the tree matches what the pinned generator produces.

## Why not the obvious alternatives

- **Matrix `go-version: [1.27.x]` with setup-go v5.** That leaves two
  places that hold the version, and `check-latest` picks whatever 1.27
  patch is newest on the day. The console moved away from exactly this in
  #24.
- **Keep golangci-lint v2.11.4 and lint with `go 1.24` only.** It refuses
  any module whose toolchain is newer than Go 1.26; there is no flag for
  that.
- **Exclude SA4006 or the gofumpt rule.** Both findings are real (dead
  code, redundant syntax), and the fixes are mechanical.
- **Skip `TestTrackingResponseWriter` on Go ≥ 1.26.** The test is still
  useful; only its status code was wrong.
- **x/tools v0.53.0 in go.mod** (the first version of this PR). It works
  and closes 20 findings, but changes the libraries the server links,
  for a build tool. Split out: note 06.
- **`go run golang.org/x/tools/cmd/stringer@v0.53.0` in each directive.**
  The same isolation, but the version would be repeated in 19 files.
- **A separate tools module (`tools/go.mod`).** Isolates as well, but adds
  a module and `-modfile` plumbing for one generator; upstream's
  `go install` step in main.go already exists.
